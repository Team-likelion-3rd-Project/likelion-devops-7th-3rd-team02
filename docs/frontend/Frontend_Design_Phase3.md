# 1. Frontend 설계 범위

3차 Frontend는 2차의 프로젝트·업무 관리 화면에 GitHub 연동, CI/CD, Kubernetes, Monitoring, 장애 대응 화면을 더해 개발·배포·운영 상태를 프로젝트 단위로 확인할 수 있도록 구성한다.

기능은 3차 구현 기능, 2차에서 유지되는 기능, 확정 전 또는 후속 기능, 3차 제외 기능으로 구분한다.

## 1.1 3차 필수 구현 기능

- 인증 만료 안내와 로그아웃
- 대시보드: 내 작업, 최근 배포, 장애 알림 배너 (사이드바에서 고른 프로젝트 기준)
- 사이드바 프로젝트 전환: 어느 화면에서든 프로젝트를 바꾸고 새 프로젝트를 만든다
- 전체 장애: 참여 중인 모든 프로젝트의 해결 안 된 장애를 한 화면에서 보고, 사이드바 배지로 확인 필요 건수를 알린다
- 프로젝트 생성 시 GitHub 저장소와 GitLab 프로젝트 연결 정보 입력
- 작업 보드: 제목 검색, 상태·담당자 필터, 정렬, 페이지네이션
- GitHub 이슈 가져오기와 작업 카드의 이슈·PR 표시
- 업무 제목·내용 수정과 상태·담당자 변경
- CI/CD: 현재 배포, 저장소 연결 상태, 파이프라인 5단계, 파이프라인 이력, 배포 이력
- 모니터링: 장애 목록과 확인·담당자 지정, 요약 지표, 추이 차트, Kubernetes 배포 상태, 파드 목록
- 프로젝트 `role`(OWNER/MEMBER)에 따른 UI 제어
- 운영 데이터의 수집 시각(`collectedAt`) 표시
- 로딩, 오류, 빈 데이터, 연결되지 않은 상태 처리

## 1.2 2차에서 유지되는 기능

다음 기능은 3차에서 화면 시안을 새로 만들지 않으며 2차 설계서를 따른다.

- 회원가입
- Header 또는 사용자 영역의 프로필 모달 (`GET /api/users/me`)
- 팀원 목록과 역할 표시, OWNER의 팀원 등록
- 업무 생성 모달
- 업무 상태 변경과 담당자 변경 (3차에서 업무 수정 모달로 통합, 4.6 참고)

## 1.3 확정 전 또는 후속 기능

| 기능 | 현재 상태 |
| --- | --- |
| 파이프라인 수동 승인, 배포 롤백 실행 | Backend가 3차에서는 조회 전용 진행을 제안했으며 실행 기능은 후순위. 화면에 버튼을 두지 않는다. |
| GitHub 계정 로그인 | Backend 우선순위 P3(선택). 구현 전에는 로그인 화면에서 해당 버튼을 표시하지 않는다. |
| 업무 삭제 | Backend 권한표에서 MEMBER의 삭제는 "정책 결정". 확정 전에는 삭제 버튼을 표시하지 않는다. |
| 프로젝트 수정·삭제, 팀원 제거, 역할 변경 화면 | Backend API는 P0~P1이지만 이번 시안 범위에 화면이 없다. 화면 포함 여부 확인이 필요하다. |
| 애플리케이션 파드 로그 조회 | 추후 논의 |
| GitHub 아이디와 DevFlow 멤버 연결 | 추후 여유가 있을 때 검토. 사용자 정보에 선택 컬럼을 추가하는 방식이 후보 |
| Slack 알림 연동 | Backend 우선순위 P3(선택) |

## 1.4 3차 제외 기능

- 휴대폰 인증, SMS 발송, 이메일 기반 비밀번호 재설정 (Backend 제외 권장)
- 앱 내 PR 리뷰 화면
- 업무 마감일과 우선순위 (Task 응답에 없음)
- 칸반 보드 드래그 앤 드롭
- 파드별 CPU·메모리 표시
- 커밋·파이프라인·배포 목록의 작성자 표시 (응답에 해당 필드가 없음)
- 대시보드의 여러 프로젝트 통합 요약 (장애만 예외로 전체 장애 화면에서 제공, 4.11)
- Grafana 화면 직접 삽입

# 2. 전체 화면 목록

DevFlow Frontend는 인증 화면, 대시보드, 프로젝트 하위 화면(작업 보드, CI/CD, 모니터링)과 각 화면의 모달로 구성한다. 로그인 이후 화면은 좌측 Sidebar로 이동한다.

## 2.1 필수 화면

| 번호 | 화면명 | 주요 기능 | 로그인 필요 | 2차 대비 |
| --- | --- | --- | --- | --- |
| 1 | 로그인 | 이메일 로그인, 인증 만료 안내 | 아니요 | 변경 |
| 2 | 회원가입 | 새로운 사용자 계정 생성 | 아니요 | 유지 |
| 3 | 대시보드 | 내 작업, 최근 배포, 장애 알림 | 예 | 신규 (2차 프로젝트 목록은 사이드바 프로젝트 전환으로 이동) |
| 4 | 작업 보드 | 업무 조회·검색·필터, GitHub 이슈·PR 표시 | 예 | 변경 (2차 프로젝트 상세의 업무 영역) |
| 5 | CI/CD | 현재 배포, 파이프라인, 배포 이력, 저장소 연결 | 예 | 신규 |
| 6 | 모니터링 | 장애, 요약 지표, 추이, Kubernetes 상태 | 예 | 신규 |
| 7 | 전체 장애 | 참여 중인 모든 프로젝트의 해결 안 된 장애 (읽기 전용) | 예 | 신규 (v2) |

## 2.2 화면별 주요 모달

### 공통 Layout (사이드바)

- 프로젝트 만들기 모달 (GitHub·GitLab 연결 입력 포함, 프로젝트 전환 드롭다운의 "새 프로젝트"에서 연다)
- 팀원 목록 모달 (팀원 박스에서 연다, OWNER는 팀원 추가)

### 대시보드

- 프로젝트 정보 모달 (이름 전체, 설명, 내 역할, 소유자, 만든 날, 팀원 수, 저장소 연결)
- 프로필 모달 (2차 유지)

### 작업 보드

- 업무 생성 모달 (2차 유지)
- 업무 수정·상태·담당자 변경 모달 (변경)
- GitHub 이슈 가져오기 모달 (신규, 시안 보드 없음 — 9.5 와이어프레임)

### CI/CD

- 연결되지 않은 상태 입력 영역 (신규, 시안 보드 없음 — 9.7 와이어프레임)

### 모니터링

- 장애 담당자 지정 선택 영역 (신규, 시안 보드 없음 — 9.9 와이어프레임)

### 확정 전 모달

- 업무 삭제 확인창 (삭제 정책 확정 후)
- 프로젝트 수정·삭제, 팀원 제거 확인창 (화면 포함 여부 확정 후)

## 2.3 화면 접근 기준

### 로그인하지 않은 사용자

- 로그인 화면
- 회원가입 화면

인증이 필요한 화면에 접근하면 로그인 화면으로 이동한다.

### 로그인한 사용자

- 대시보드와 참여 중인 프로젝트의 작업 보드, CI/CD, 모니터링
- 프로필 모달

### 프로젝트 OWNER와 MEMBER

Backend 권한표(Issue #147 4-3)를 기준으로 한다.

| 기능 | OWNER | MEMBER |
| --- | --- | --- |
| 프로젝트·작업·CI/CD·모니터링 조회 | O | O |
| 업무 생성 | O | O |
| 업무 수정, 상태·담당자 변경 | O | O |
| 업무 삭제 | O | 미정 |
| 팀원 등록 | O | X |
| GitHub·GitLab 연결 등록·해제 | 미정 | 미정 |
| 장애 확인, 담당자 지정 | 미정 | 미정 |

권한이 정해지지 않은 항목은 화면에서 구분하지 않고 모든 사용자에게 표시하며, Backend의 `403 Forbidden`을 처리한다. 확정되면 해당 버튼을 role에 따라 숨기거나 비활성화한다.

현재 사용자의 role은 프로젝트 조회 응답의 `role`을 사용한다. 2차의 현재 사용자·`ownerId`·멤버 목록 조합 판별은 응답에 `role`이 포함되면 대체한다.

## 2.4 3차 제외 기능 적용 화면

| 적용 화면 | 제외 기능 | 현재 처리 |
| --- | --- | --- |
| CI/CD | 승인·롤백 실행 | 버튼 미제공, 조회 전용 |
| CI/CD, 대시보드 | 작성자 표시 | 응답에 필드가 없어 표시하지 않음 |
| 작업 보드 | 마감일 | Task에 필드가 없어 표시·정렬하지 않음 |
| 작업 보드 | 업무 삭제 | 정책 확정 전 버튼 미제공 |
| 모니터링 | 파드별 CPU·메모리, 파드 로그 | 미제공 |
| 로그인 | GitHub 계정 로그인 | 구현 전에는 버튼 미표시 |

# 3. 전체 사용자 흐름

3차의 핵심 흐름은 프로젝트에 GitHub 저장소와 GitLab 프로젝트를 연결하고, 작업을 진행하면서 배포와 운영 상태까지 한 곳에서 확인하는 순서로 구성한다.

## 3.1 전체 핵심 흐름

> 로그인  
> → 대시보드 조회  
> → 프로젝트 생성 및 GitHub·GitLab 연결  
> → 작업 보드에서 GitHub 이슈 가져오기  
> → 개발 시작 (Backend가 Webhook으로 업무 상태 자동 변경)  
> → PR 머지 (Backend가 업무를 완료로 자동 변경)  
> → CI/CD에서 파이프라인과 배포 확인  
> → 모니터링에서 장애, 지표, 파드 상태 확인  
> → 장애 확인 및 담당자 지정

## 3.2 로그인 및 인증 만료 흐름

> 서비스 접속  
> → 이메일과 비밀번호 입력  
> → 로그인 성공  
> → Access Token 저장  
> → `GET /api/users/me`로 현재 사용자 확인  
> → 대시보드 이동

- 인증이 필요한 API 요청이 `UNAUTHORIZED`를 받으면 저장된 인증 정보를 삭제하고 `/login?reason=expired`로 이동한다.
- 로그인 화면은 `reason=expired`일 때 "로그인이 만료됐어요. 다시 로그인해 주세요." 안내를 표시한다. 이 안내는 2차에서 이미 사용한 이동 방식을 유지한다.
- Refresh Token(`POST /api/auth/refresh`)은 Backend 우선순위 P2다. 도입 전에는 만료 시 로그인 화면으로 이동한다.
- 로그아웃은 `POST /api/auth/logout`(P2)이 제공되기 전까지 2차와 같이 Frontend의 인증 정보 삭제로 처리한다.

## 3.3 프로젝트 생성 및 저장소 연결 흐름

> 사이드바 프로젝트 전환 드롭다운에서 새 프로젝트 선택 (프로젝트가 없으면 대시보드 안내에서 선택)  
> → 이름과 설명 입력  
> → (선택) GitHub 저장소 주소 입력  
> → (선택) GitLab 프로젝트 경로 입력  
> → 생성 요청  
> → 생성된 프로젝트의 `projectId`로 연결 요청  
> → 새 프로젝트로 전환하고 그 프로젝트의 대시보드로 이동

- 연결 API는 `projectId` 경로를 사용하므로 프로젝트 생성이 먼저 완료되어야 한다. Frontend는 생성 성공 후 연결 API를 이어서 호출한다.
- 저장소 주소와 경로는 입력하지 않아도 프로젝트를 만들 수 있다.
- 프로젝트 생성은 성공했지만 연결이 실패한 경우, 프로젝트는 유지하고 연결 실패 안내를 표시한다. 이후 CI/CD 화면에서 다시 연결한다 (3.6 참고).
- 연결 전 저장소 확인 기능은 제공하지 않는다.

## 3.4 작업 조회 및 관리 흐름

> 작업 보드 진입  
> → 상태별 업무 조회  
> → 제목 검색, 상태 칩 또는 담당자 선택, 정렬 선택  
> → 페이지 이동  
> → 업무 카드 선택  
> → 오른쪽 상세 패널 확인  
> → 수정 버튼으로 제목·내용·상태·담당자 변경

- 검색, 필터, 정렬은 `GET /api/projects/{projectId}/tasks`의 Query Parameter로 전달한다.
- 업무 카드의 이슈 번호와 PR 상태는 업무 응답에 포함된 연결 정보를 사용한다 (6.4, 10.2 참고).
- 상태는 `TODO`, `IN_PROGRESS`, `DONE`을 사용한다.

## 3.5 GitHub 이슈 가져오기 및 자동 상태 변경 흐름

> 작업 보드에서 GitHub 이슈 가져오기 선택  
> → 이슈 목록 조회  
> → 가져올 이슈 선택  
> → 업무 생성  
> → 작업 카드에 이슈 번호 표시

> GitHub Branch·Commit 발생  
> → Backend Webhook 수신  
> → 업무가 `IN_PROGRESS`로 변경  
> → PR 머지  
> → 업무가 `DONE`으로 변경  
> → 작업 보드 재조회 시 반영

- 상태 자동 변경은 Backend가 처리하며 Frontend는 변경된 업무를 조회해 표시한다.
- 이미 가져온 이슈는 중복 업무가 만들어지지 않으며, Backend의 중복 응답을 오류 안내로 표시한다.
- 가져온 업무의 담당자는 비어 있고 사용자가 지정한다.
- 자동 상태 변경 이력 표시는 Backend가 "검토" 단계라 이번 화면에서 제외한다.

## 3.6 CI/CD 확인 흐름

> CI/CD 진입  
> → 저장소 연결 상태 확인  
> → 현재 배포의 이미지 태그·리비전·환경 확인  
> → 진행 중 또는 최근 파이프라인의 5단계 상태 확인  
> → 파이프라인 이력과 배포 이력 조회

- 파이프라인 5단계는 BUILD, TEST, IMAGE, VERIFY, DEPLOY이며 화면에는 Build, Test, Image, Verify, Deploy로 표시한다.
- 저장소가 연결되지 않은 프로젝트는 연결 입력 영역을 표시한다 (9.7).
- 승인과 롤백은 조회 전용 방침에 따라 표시하지 않는다.

## 3.7 장애 확인 및 담당자 지정 흐름

> 모니터링 진입 또는 대시보드 배너 선택  
> → 장애 목록 조회  
> → 장애 확인(ack)  
> → 담당자 지정  
> → 목록 갱신

- 장애 상태는 `OPEN`, `ACKNOWLEDGED`, `RESOLVED` 순서로 진행한다.
- 확인 후에도 담당자 지정은 별도로 수행할 수 있다.
- Alertmanager 알림과 DevFlow 장애 상태의 동기화 정책은 Backend가 구현 전에 정한다.

## 3.8 모니터링 추이 범위 변경 흐름

> 모니터링 진입  
> → 기본 범위(1시간)의 요약·추이 조회  
> → 범위 선택(1시간, 6시간, 24시간)  
> → 같은 요청에 `range`만 바꿔 재조회

- 허용되는 `range` 값은 Backend 확인이 필요하다 (10.2).

# 4. 화면별 상세 구성

## 4.1 공통 Layout

### 화면 목적

로그인한 사용자가 어느 화면에서든 현재 프로젝트를 확인하고 바꾸며, 주요 화면으로 이동하고 로그아웃할 수 있도록 한다.

### 주요 구성 요소

- 맨 윗줄(모든 프로젝트 영역): 로고 아이콘(선택하면 대시보드로 이동), 전체 장애 버튼(확인 필요 건수 배지)
- 프로젝트 전환 드롭다운 (여기부터 선택한 프로젝트 영역): 현재 프로젝트 이름, 참여 중인 프로젝트 목록과 프로젝트별 내 역할, 새 프로젝트
- 팀원 박스: 내 역할(`role`)과 팀원 수 (선택하면 팀원 목록 모달)
- 이동 메뉴: 대시보드, 작업 보드, CI/CD, 모니터링
- 현재 사용자 이름과 로그아웃
- 페이지 콘텐츠 영역

### 핵심 동작

- 현재 메뉴를 강조한다.
- 프로젝트를 고르는 곳은 사이드바의 프로젝트 전환 드롭다운 한 곳이다.
- 작업 보드, CI/CD, 모니터링에서 프로젝트를 바꾸면 보던 메뉴를 유지한다. (예: A의 작업 보드 → B의 작업 보드)
- 현재 프로젝트는 URL의 프로젝트, 없으면 마지막으로 본 프로젝트, 처음이면 첫 번째 프로젝트다. 마지막으로 본 프로젝트는 브라우저에 저장하고, 저장할 수 없으면 첫 번째 프로젝트로 연다.
- 드롭다운은 방향키로 항목을 이동하고, Esc나 바깥을 선택하면 닫힌다.
- 긴 프로젝트 이름은 드롭다운 버튼과 목록, 대시보드 모두 한 줄 말줄임으로 표시하고 마우스를 올리면 전체 이름을 보여준다. 전체 이름은 프로젝트 정보 모달에서 줄바꿈해 모두 보여준다 (4.4).
- 참여 중인 프로젝트가 없으면 드롭다운에 "프로젝트 없음"을 표시하고 팀원 박스는 숨긴다.
- 대시보드 메뉴는 로고 아이콘과 별도로 유지한다.
- 전체 장애 버튼은 확인 필요(OPEN) 장애가 있을 때만 숫자 배지를 표시하고, 선택하면 전체 장애 화면으로 이동한다 (4.11). 배지 건수는 1분마다 다시 불러오되 탭이 보이지 않으면 멈추고, 다시 보이면 바로 불러온다. 장애를 확인하거나 담당자를 바꾸면 바로 다시 불러온다.
- 주소의 프로젝트가 내 프로젝트 목록에 없으면(팀에서 빠졌거나 없는 프로젝트) 화면 대신 "접근할 수 없는 프로젝트" 안내와 대시보드 이동 버튼을 보여준다.
- 사용자 이름 영역을 선택하면 프로필 모달을 표시한다 (2차 유지, 위치는 10.3 참고).
- 로그아웃 시 저장된 JWT와 사용자 정보를 삭제하고 로그인 화면으로 이동한다.
- 다크와 화이트 두 가지 시안을 준비한다. 적용 방식은 10.4에서 확정한다.

## 4.2 로그인 화면

### 화면 목적

가입된 사용자가 이메일과 비밀번호로 로그인할 수 있도록 한다.

### 주요 구성 요소

- 서비스 소개 문구와 작업→PR→빌드→배포→상태 흐름 표시
- 인증 만료 안내
- 이메일 입력창, 비밀번호 입력창
- 로그인 버튼
- GitHub로 계속하기 버튼 (P3 구현 시에만 표시)
- 회원가입 이동 링크

### 핵심 동작

- 로그인 성공 시 Access Token을 저장하고 현재 사용자를 조회한 뒤 대시보드로 이동한다.
- 로그인 실패 시 오류 메시지를 표시한다.
- 처리 중에는 로그인 버튼을 비활성화한다.
- `reason=expired`일 때만 인증 만료 안내를 표시한다.

## 4.3 회원가입 화면

2차 설계서 4.3을 따른다. 변경 사항은 없다.

## 4.4 대시보드 화면

### 화면 목적

사이드바에서 고른 프로젝트에서 오늘 확인할 것(장애, 내 작업, 최근 배포)을 먼저 보여준다. 다른 화면과 같이 프로젝트 하나만 다룬다.

### 주요 구성 요소

- 인사 문구, 현재 프로젝트 이름과 "프로젝트 정보" 버튼, 마지막 수집 시각
- 장애 알림 배너 (열린 장애가 있을 때)
- 환경 요약 자리 (화면 범위 확정 후 표시, Backend Wiki "Backend API 구현 목록" 12장 E1)
- 내 작업 목록
- 최근 배포 목록
- 프로젝트가 없을 때: 첫 프로젝트 만들기 안내와 프로젝트 만들기 버튼

### 표시 정보와 출처

| 영역 | 표시 정보 | 출처 |
| --- | --- | --- |
| 장애 배너 | 확인되지 않은 장애 건수와 요약 | 장애 목록 (`OPEN`) |
| 내 작업 | 제목, 이슈 번호, PR 상태, 상태 | `GET /api/users/me`의 사용자 id로 `assigneeId` 필터 |
| 최근 배포 | 이미지 태그, 시각, 상태 | 배포 목록 |
| 마지막 수집 | 수집 시각 | 응답의 `collectedAt` |

### 핵심 동작

- 장애 배너를 선택하면 모니터링 화면으로 이동한다.
- 내 작업과 최근 배포의 "열기" 링크는 작업 보드와 CI/CD로 이동한다.
- 내 작업, 최근 배포, 장애 배너는 현재 선택된 프로젝트 기준으로 조회한다.
- 열린 장애가 없으면 배너를 표시하지 않는다.
- 프로젝트를 바꾸거나 만드는 것은 사이드바 프로젝트 전환 드롭다운에서 한다 (4.1). 바꾸면 위 영역이 갱신된다.
- "프로젝트 정보"를 선택하면 프로젝트 정보 모달을 연다. 이름 전체, 설명, 내 역할, 소유자, 만든 날, 팀원 수, GitHub 저장소(새 탭 링크), GitLab 경로를 보여준다.
  - 저장소가 연결되지 않았으면 "연결 안 됨"을 표시하고, OWNER에게만 "CI/CD에서 연결" 링크를 보여준다.
  - 프로젝트 수정·삭제 버튼은 두지 않는다 (1.3).
- 새 프로젝트를 만들면 그 프로젝트의 대시보드로 이동한다. 비어 있는 영역의 안내(작업 보드 열기, CI/CD 열기)가 다음 할 일을 알려 준다.

## 4.5 작업 보드 화면

### 화면 목적

프로젝트의 업무를 상태별로 확인하고 검색·필터하며 GitHub 이슈·PR과의 연결 상태를 확인할 수 있도록 한다.

### 주요 구성 요소

- 제목 검색창
- 상태 칩 (전체, 할 일, 진행 중, 완료)
- 담당자 선택, 정렬 선택
- GitHub 이슈 가져오기 버튼, 작업 추가 버튼
- 상태별 컬럼과 업무 카드 (제목, 이슈 번호, PR 배지, 담당자 이름)
- 페이지네이션
- 오른쪽 상세 패널 (제목, 상태, 설명, 담당자, GitHub 이슈, PR 링크, 수정 버튼)

### 핵심 동작

- 검색어는 업무 제목에만 적용한다 (`keyword`).
- 상태 칩을 선택하면 해당 상태의 업무만 표시한다 (`status`).
- 담당자 선택은 프로젝트 팀원 중에서 고르며 값은 `userId`를 사용한다 (`assigneeId`).
- 정렬과 페이지(`sort`, `page`, `size`)를 함께 전달한다. 한 페이지는 12건으로 한다.
- 컬럼의 건수는 상태별 조회 결과의 전체 건수를 사용한다.
- 업무 카드를 선택하면 오른쪽에 상세 패널을 연다. 선택한 업무가 없으면 상세 패널 없이 보드가 전체 폭을 쓴다.
- 상세 패널은 닫기 버튼, Esc, 같은 카드 다시 선택으로 닫고, 닫으면 포커스를 그 카드로 돌려준다. 모달이 열려 있을 때 Esc는 모달만 닫는다.
- 카드 제목은 한 줄 말줄임으로 표시하고, 상세 패널에서는 줄바꿈해 모두 보여준다.
- PR 배지의 값은 열림, 리뷰 중, 머지됨을 구분해 표시하며 "GitHub에서 보기"는 새 탭으로 연다.
- 수정 버튼은 업무 수정 모달을 연다 (4.6).
- 삭제 버튼은 표시하지 않는다 (정책 확정 전).
- 정렬 기준은 최근 수정순을 기본으로 하며, 마감일 정렬은 제공하지 않는다.

---

## 4.6 업무 수정·상태·담당자 변경 모달

### 화면 목적

선택한 업무의 제목과 내용을 수정하고 상태와 담당자를 변경할 수 있도록 한다.

### 주요 구성 요소

- 업무 제목, 업무 내용 입력창
- 담당자 선택, 상태 선택
- 저장, 취소 버튼
- 처리 오류 메시지

### 핵심 동작

- 제목과 내용 수정은 `PATCH /api/projects/{projectId}/tasks/{taskId}`를 사용한다.
- 상태와 담당자 변경은 2차의 전용 API를 그대로 사용한다.
- 변경한 항목만 해당 API를 호출한다.
- 저장 성공 후 작업 보드를 갱신하고 실패 시 기존 값을 유지한다.
- 이슈에서 가져온 업무의 이슈·PR 연결 정보는 수정하지 않는다.

## 4.7 CI/CD 화면

### 화면 목적

현재 배포된 버전, 저장소 연결 상태, 파이프라인 단계와 이력, 배포 이력을 확인할 수 있도록 한다.

### 주요 구성 요소

- 마지막 수집 시각
- 현재 배포 패널: 이미지 태그, 리비전, 환경, 커밋, 배포 시각, 상태
- 저장소 연결 패널: GitHub 저장소와 연결됨 표시, GitLab 프로젝트와 매핑됨 표시
- 진행 중 파이프라인: Build, Test, Image, Verify, Deploy의 상태와 단계별 소요 시간
- 파이프라인 이력 표: 번호, 브랜치, 커밋, 상태, 시작, 소요 시간
- 배포 이력 표: 리비전, 이미지 태그, 커밋, 환경, 상태, 배포 시각
- 각 이력 표의 페이지네이션

### 핵심 동작

- 현재 배포는 배포 목록의 최신 항목을 사용한다.
- 파이프라인 단계는 완료, 진행 중, 대기를 구분해 표시하고 실패한 단계는 이력 표의 상태에 "실패 (Test)"처럼 단계명을 함께 표시한다.
- 소요 시간은 시작 시각과 완료 시각의 차이로 계산한다.
- 파이프라인과 배포 이력은 `page`, `size`로 조회한다.
- 커밋은 SHA 앞 7자리를 표시한다. 커밋 메시지는 응답에 포함될 때만 함께 표시한다 (10.2).
- 승인·롤백 버튼과 작성자는 표시하지 않는다.
- 저장소가 연결되지 않았으면 해당 패널에 입력 영역을 표시한다 (9.7).

---

## 4.8 모니터링 화면

### 화면 목적

장애를 먼저 확인하고 서비스의 요약 지표, 추이, Kubernetes 배포·파드 상태를 확인할 수 있도록 한다.

### 주요 구성 요소

- 마지막 수집 시각, 기간 선택(1시간, 6시간, 24시간)
- 장애 목록: 심각도, 제목, 발생 후 경과, 출처, 담당자, 상태, 확인·담당자 지정 버튼
- 요약 지표: HTTP 요청 수, 오류율, 평균 응답 시간, 레플리카
- 추이 차트: 오류율, 응답 시간, CPU와 메모리
- 배포 상태 표: 목표, 사용 가능, 준비됨, 최신 버전 수
- 파드 표: 이름, 상태, 준비, 재시작, 생성, 이미지

### 핵심 동작

- 장애 목록을 가장 위에 표시하고 확인되지 않은 건수를 헤더에 표시한다.
- 확인 버튼은 `OPEN` 상태의 장애에만 활성화한다.
- 담당자 지정은 프로젝트 팀원 목록에서 선택한다 (9.9).
- 기간을 바꾸면 요약과 추이를 같은 `range`로 다시 조회한다.
- CPU와 메모리는 서비스 전체 값을 한 차트에 함께 표시한다.
- 파드의 재시작 횟수가 0이 아니면 강조한다.
- 지표 임계값 기준선은 표시하지 않는다 (응답에 기준값이 없음).

---

## 4.9 프로젝트 만들기 모달

### 화면 목적

새 프로젝트를 만들면서 GitHub 저장소와 GitLab 프로젝트 연결 정보를 함께 입력할 수 있도록 한다.

### 주요 구성 요소

- 프로젝트 이름, 설명
- GitHub 저장소 주소
- GitLab 프로젝트 경로와 안내 문구
- 취소, 프로젝트 만들기 버튼

### 핵심 동작

- 이름만 필수이며 저장소 정보는 선택이다.
- 프로젝트 생성 후 입력한 연결 정보로 연결 API를 호출한다 (3.3).
- GitLab은 프로젝트 목록 조회 API가 없어 경로를 직접 입력한다.
- GitHub·GitLab 접근 토큰 입력 여부는 Backend 확인 후 결정한다 (10.2).

## 4.11 전체 장애 화면

### 화면 목적

여러 프로젝트에 참여하는 사용자가 지금 보고 있지 않은 프로젝트의 장애까지 한 화면에서 알 수 있도록 한다.

### 주요 구성 요소

- 제목과 안내 문구 (확인과 담당자 지정은 각 프로젝트의 모니터링에서 한다)
- 상태 칩: 해결 안 됨(기본), 확인 필요(건수), 최근 해결(24시간)
- 프로젝트별 묶음: 프로젝트 이름, 건수, "모니터링 열기"
- 장애 행: 심각도, 제목, 요약, 경과 시간과 출처, 현재 안정화됨, 담당자 지정됨 / 담당자 없음, 확인 필요 / 확인함

### 핵심 동작

- 읽기 전용이다. 장애를 선택하면 그 프로젝트의 모니터링 화면으로 이동하고, 사이드바의 현재 프로젝트도 함께 바뀐다.
- 담당자는 이름 대신 지정 여부만 표시한다. 담당자 선택지가 프로젝트마다 달라 지정은 모니터링에서만 한다.
- 묶음 순서는 응답 순서(발생 최신순)를 따른다.
- 최근 해결은 선택했을 때만 `status=RESOLVED`로 따로 조회한다(API가 최근 24시간만 돌려준다). 행에는 발생 시각과 해결 시각(`resolvedAt`), "해결됨"을 표시한다. 해결된 장애는 모니터링·대시보드 배너·배지에는 나오지 않는다.
- 장애는 삭제되지 않고 해결 상태로 남는다. 24시간보다 오래된 해결 장애 조회는 3차 범위 밖이다.
- 장애 기준은 모든 화면이 같다: 열린 장애는 `OPEN`·`ACKNOWLEDGED`, 확인 필요는 `OPEN`이다.

# 5. 로딩·오류·빈 데이터 처리

2차 설계서 5장의 공통 원칙(중복 요청 방지, 오류 시 입력 유지, 다시 시도 제공, 인증 만료 시 로그인 이동)을 그대로 따른다. 3차에서 추가되는 상태만 정의한다.

## 5.1 로딩 상태

| 영역 | 처리 |
| --- | --- |
| 작업 보드 | 검색·필터·페이지 변경 중 기존 목록을 유지하고 로딩 표시 |
| CI/CD, 모니터링 | 패널 단위 로딩 (한 영역의 지연이 다른 영역을 가리지 않음) |
| 추이 차트 | 기간 변경 중 차트 영역에 로딩 표시 |
| 프로젝트 만들기 | 생성과 연결 요청 중 버튼 비활성화 |

### 예시 메시지

> 업무를 불러오는 중입니다.  
>
> 파이프라인을 불러오는 중입니다.  
>
> 모니터링 데이터를 불러오는 중입니다.

## 5.2 오류 상태

| 오류 유형 | 처리 방식 |
| --- | --- |
| 외부 연동 조회 오류 (GitHub, GitLab, Kubernetes, Prometheus) | 해당 패널에만 오류와 다시 시도 표시, 다른 영역은 유지 |
| 연결 정보 등록 오류 | 입력 내용을 유지하고 오류 표시 |
| 프로젝트 생성 성공, 연결 실패 | 프로젝트는 유지하고 연결 실패 안내 표시 |
| 이슈 중복 가져오기 | 이미 가져온 이슈라는 안내 표시 |
| 장애 확인·담당자 지정 오류 | 기존 상태 유지, 실패 메시지 표시 |
| 권한 오류 | 해당 기능을 사용할 권한이 없다는 안내 표시 |

오류 코드별 문구는 Backend가 3차 오류 코드를 확정한 뒤 2차 5.2의 목록에 추가한다.

2차 설계서 5.3과 같다. 로그인 화면의 만료 안내는 4.2를 따른다.

## 5.4 빈 데이터 상태

| 화면 | 안내 문구 | 제공 기능 |
| --- | --- | --- |
| 대시보드 내 작업 | 나에게 할당된 업무가 없어요. | 작업 보드 열기 |

## 6.9 장애 API

| 기능 | Method | API 경로 | 구분 |
| --- | --- | --- | --- |
| 장애 목록 | `GET` | `/api/projects/{projectId}/incidents` | 확정 |
| 장애 상세 | `GET` | `/api/projects/{projectId}/incidents/{incidentId}` | 확정 |
| 장애 확인 | `PATCH` | `/api/projects/{projectId}/incidents/{incidentId}/ack` | 확정 |
| 담당자 변경 | `PATCH` | `/api/projects/{projectId}/incidents/{incidentId}/assignee` | 확정 |
| 내 전체 프로젝트 장애 | `GET` | `/api/users/me/incidents?status=OPEN,ACKNOWLEDGED` | 확정 (FE 요청, Wiki I7) |

상태는 `OPEN` → `ACKNOWLEDGED` → `RESOLVED`다. 응답 필드는 6.10의 요청 사항이다.

- 장애 객체는 모든 응답에 `projectId`, `projectName`을 포함한다.
- 이미 확인된 장애를 다시 확인하면 200과 현재 장애를 돌려준다(먼저 확인한 사람·시각 유지). 해결된 장애를 확인하면 409 `INVALID_INCIDENT_STATUS`다. Frontend는 확인 후 성공·실패와 관계없이 목록을 다시 불러온다.
- 내 전체 프로젝트 장애: 내가 팀원인 프로젝트만, `status`는 쉼표로 여러 값(생략 시 `OPEN`, `ACKNOWLEDGED`), 발생 최신순 최대 100건. 응답은 `{ openCount, incidents }`이고 `openCount`는 `status`와 무관한 전체 `OPEN` 건수다.

## 6.10 Backend에 추가 요청한 사항

| 항목 | 요청 내용 | 화면 |
| --- | --- | --- |
| Task와 GitHub 이슈·PR 연결 정보 | Task 조회 응답(목록, 상세)에 이슈 번호·URL, PR 번호·상태·URL 포함 | 작업 보드 |
| 장애 응답 필드 | 제목, 상태, 심각도, 발생 시각, 출처, 담당자(`userId`) | 모니터링, 대시보드 |
| 연결 시 입력 값 (질문) | GitHub·GitLab 연결에 저장소 주소와 경로 외에 접근 토큰 입력이 필요한지 | 프로젝트 만들기, CI/CD |

2차 6.7, 6.8을 따른다. 목록 응답의 페이지 정보(전체 건수, 전체 페이지 수)가 포함되는지는 10.2에서 확인한다.

## 6.12 최종 구현 확인 사항

- 프로젝트 `role`은 프로젝트 조회 응답에서 받는다.
- 담당자 값은 작업과 장애 모두 `userId`를 사용한다.
- 작업 검색은 제목에만 적용한다.
- 파이프라인과 배포 이력에만 `page`, `size`를 적용한다.
- 운영 데이터 화면은 `collectedAt`을 표시한다.
- 승인·롤백 실행 API는 호출하지 않는다.
- Frontend는 GitHub, GitLab, Kubernetes, Prometheus에 직접 접근하지 않고 Backend API만 호출한다.

## 7.3 컴포넌트 구성 원칙

- 화면 단위 코드는 `pages`에서 관리하고 영역별 UI는 `components` 하위 폴더로 분리한다.
- 목록·필터·페이지 상태와 API 호출은 화면별 Custom Hook에서 관리한다.
- Backend 요청은 `api` 모듈에서 관리한다.
- 한 영역의 조회 실패가 다른 영역을 가리지 않도록 영역별로 로딩·오류를 처리한다.
- 같은 데이터(예: 팀원 목록)를 여러 컴포넌트가 중복 호출하지 않는다.
- 차트는 3종(오류율, 응답 시간, CPU·메모리)이며 라이브러리 사용 여부는 구현 시 정한다.
- 확정 전 기능(삭제, 승인·롤백)을 위한 컴포넌트는 선행 구현하지 않는다.

# 8. API 주소 및 환경변수 관리

2차 설계서 8장을 따른다. 3차에서 추가되는 환경변수는 없다.

3차의 모든 외부 연동(GitHub, GitLab, Kubernetes, Prometheus)은 Backend를 통해 호출하므로 Frontend에는 해당 서비스의 주소나 토큰을 두지 않는다.

# 10. 팀원 협의 및 확인 사항

## 10.1 확정된 사항

### Backend 확인 결과 (Issue #147)

- GitLab 프로젝트 연결 API(`POST/GET/DELETE .../integrations/gitlab`) 추가
- 장애 조회·확인·담당자 변경 API 추가, 상태는 `OPEN` → `ACKNOWLEDGED` → `RESOLVED`
- 장애 출처는 Prometheus/Alertmanager 기반으로 우선 검토
- 프로젝트 조회 응답에 현재 사용자의 `role` 포함
- GitHub 커밋·PR 응답에 `githubLogin`, 매핑 가능 시 `memberId` 포함
- 모니터링·Kubernetes·파이프라인 응답에 `collectedAt` 포함
- 파이프라인·배포 목록에 `page`, `size` 적용
- 모니터링 요약에 `range` 옵션과 시계열 데이터 지원
- 파이프라인 승인과 롤백 실행은 3차에서 조회 전용, 실행은 후순위

### Frontend 결정

- 화면 시안은 다크와 화이트 두 가지로 확정
- 작업 담당자는 DevFlow 멤버 이름으로 표시 (GitHub 아이디 표시 없음)
- 커밋·파이프라인·배포 작성자는 표시하지 않음
- 승인·롤백 버튼, 업무 삭제 버튼, 파드 로그는 표시하지 않음

## 10.2 Backend 담당자 확인 요청

- Task 조회 응답의 GitHub 이슈·PR 연결 정보 포함 (6.10)
- 장애 응답 필드: 제목, 상태, 심각도, 발생 시각, 출처, 담당자(`userId`)
- GitHub·GitLab 연결 시 사용자가 입력할 값에 접근 토큰이 포함되는지
- `monitoring/summary`의 허용 `range` 값 (화면은 1시간, 6시간, 24시간)
- 파이프라인과 배포 응답에 커밋 메시지가 포함되는지 (없으면 SHA만 표시)
- 목록 응답에 전체 건수와 전체 페이지 수가 포함되는지
- 작업 목록 `sort`의 허용 값 (화면은 최근 수정순 기본)
- 상태별 업무 전체 건수를 얻는 방법 (상태별 조회의 전체 건수 사용을 전제)
- Alertmanager와 DevFlow 장애 상태의 동기화 정책 (자동 해결 처리 여부)
- Task 삭제의 MEMBER 권한 정책
- GitHub·GitLab 연결 등록·해제와 장애 확인·담당자 지정의 권한 (OWNER 한정 여부)
- 3차 신규 API의 오류 코드

## 10.3 Frontend 내부 결정 사항

- 대시보드의 내 작업, 최근 배포, 장애 배너는 현재 선택된 프로젝트 기준으로 조회
- 프로젝트 만들기는 생성 후 연결 API를 이어서 호출
- 현재 사용자 id는 `GET /api/users/me`로 확보
- 프로필 모달은 Sidebar의 사용자 영역에서 연다 (2차 Header 위치 대체)
- 프로젝트 전환은 사이드바 프로젝트 전환 드롭다운 한 곳에서 한다. 대시보드에는 프로젝트 목록을 두지 않는다 (v2)
- 팀원 목록(2차 `MemberPanel`)은 사이드바 팀원 박스에서 모달로 연다 (v2)
- 마지막으로 본 프로젝트를 브라우저에 저장해 다시 들어오면 그 프로젝트로 연다 (v2)
- 새 프로젝트를 만들면 그 프로젝트의 대시보드로 이동한다 (v2)
- 전체 장애는 읽기 전용으로 두고, 확인·담당자 지정은 각 프로젝트의 모니터링에서만 한다 (v2)
- 상태 칩은 상태 필터로 동작하고 담당자 필터와 함께 적용
- 한 페이지는 12건
- 추이 차트는 오류율, 응답 시간, CPU와 메모리 3종
- 저장소 조회의 기본 브랜치는 표시하지 않음

## 10.4 팀 전체 확인 사항

- 프로젝트 수정·삭제, 팀원 제거, 역할 변경 화면을 3차에 포함할지 (Backend API는 P0~P1이나 이번 시안에 화면 없음)
- 2차 `HealthSection`, `ServiceStatusPanel`을 3차 모니터링 화면이 대체하는지, 별도로 유지하는지
- 다크·화이트 테마 적용 방식 (사용자 선택 토글, 시스템 설정 따름, 하나만 적용)
- GitHub 계정 로그인(P3) 구현 여부, 구현하지 않으면 버튼 미표시
- GitHub 아이디와 DevFlow 멤버 연결 기능을 추후 추가할지 (사용자 정보에 GitHub 아이디 컬럼을 두는 방식이 후보)
